# 4. API contract and type generation

- **Status:** Accepted
- **Date:** 2026-08-23
- **Related:** [0001](./0001-application-stack-and-topology.md),
  [0008](./0008-authorization-capabilities-and-audit.md),
  [0010](./0010-schema-generated-code-and-migration-conventions.md)

## Context

[ADR 0001](./0001-application-stack-and-topology.md) makes Go the authoritative application layer and
routes every browser interaction through it. The consequence is that essentially every feature in
[`PLAN.md`](../../PLAN.md) costs a Go handler plus a TypeScript caller, and the system will
accumulate a large API surface: roster CRUD, import preview and commit, catalog authoring, session
lifecycle transitions, survey definition and submission, ranked choices, tags, pairings, staffing,
solve and re-solve, manual assignment operations, ten reporting endpoints, publishing, and share-link
management.

Two properties of this project raise the value of a machine-checked contract above the usual:

- **Most of the code is written by agents in parallel worktrees.** Two agents implementing adjacent
  endpoints cannot see each other's work. Hand-written Go structs and hand-written TypeScript
  interfaces drifting apart is the most likely silent defect class in the entire build, and it is
  invisible to both the Go compiler and `tsc`.
- **Several domain distinctions are semantically load-bearing and structurally invisible.** SPEC
  §13.5 requires *Rated*, *Unrated* and *No response* to remain distinct; §16.5 defines eighteen
  stable warning identifiers; §17.4.1 defines a five-point ordered quality scale. Each of these is a
  closed set that both sides must agree on exactly. A generated contract makes disagreement a build
  failure; hand-written types make it a bug report from an organiser in week three.

Today the frontend hand-writes its types (`frontend/src/lib/api.ts` validates the health response by
hand). That is proportionate for one endpoint and will not survive fifty.

Any candidate had to satisfy three criteria:

1. Drift between Go and TypeScript fails CI, not review.
2. The closed sets above are generated, not restated.
3. An agent adding an endpoint has one obvious place to declare it.

## Decision

**Candidate B — Go is the source of truth — implemented with [Huma v2](https://huma.rocks) over the
existing chi router via the `humachi` adapter.**

- An operation is declared once, as a `huma.Register` call with typed input and output structs. The
  OpenAPI 3.1 document is derived from those types rather than maintained alongside them.
- `openapi.json` is generated by a Go command and **committed**, so the contract is reviewable in a
  diff. A CI check regenerates and fails on any difference.
- TypeScript types are generated from that document **during the frontend build** and are not
  committed, which makes staleness structurally impossible rather than merely detected. See
  [ADR 0010](./0010-schema-generated-code-and-migration-conventions.md).
- Errors follow Huma's default RFC 9457 `application/problem+json`, with a Go registry of stable
  problem-type slugs generated into the contract.
- Operation metadata carries the required capability, which
  [ADR 0008](./0008-authorization-capabilities-and-audit.md) enforces with a default-deny middleware
  and an enumeration test over every registered operation.

Criterion 3 is the one that decides it. With parallel agents who cannot see each other's work, an
endpoint that is three artifacts — YAML, Go handler, TypeScript caller — will drift at the YAML,
because nothing compiles against it. Making the Go registration the single declaration removes the
opportunity.

## Alternatives considered

**A. A hand-written OpenAPI document as the source of truth**, generating Go server interfaces with
`oapi-codegen` and TypeScript with `openapi-typescript`. Rejected. Its real advantage — a contract
reviewable independently of either implementation — is worth much less here than it would be with a
separate frontend team, because there is one author of both sides. Against that it makes every
endpoint a third artifact, and it is the artifact with no compiler.

**C. tRPC-style shared schema.** Rejected in advance: it assumes a TypeScript server.

**D. Hand-written on both sides with contract tests.** Rejected. The failure mode is silent and the
mitigation is discipline, which does not scale to parallel agents.

## Consequences

- Huma is a framework commitment layered on chi, and the scaffolded health handler, middleware chain
  and error shape are reworked onto it. That rework is small now and grows with every endpoint, which
  is why the decision was scheduled before Phase 1's roster CRUD.
- The API's error shape changes from `{"error": "..."}` to RFC 9457 problem details. Field-level
  validation errors carry a `location`, which the frontend renders inline — removing the need for a
  client-side validation library that would restate server constraints.
- Two generated artifacts are committed and must never be hand-merged; see ADR 0010.
- Every closed set added in a later phase — §16.5's eighteen warning identifiers, §17.4.1's
  five-point quality scale, §13.5's *Rated* / *Unrated* / *No response* distinction — now has a
  mechanical path from one declaration to both languages.
